# Delivery plan: AGE-110, AGE-114, AGE-113, AGE-94

Date: 2026-11-18. Approved by the owner on 2026-11-18.

## Goal

Make the framework usable from the first install: any set of hosts installs in one run, the first session sets itself up, and every question or choice is shown with native host controls. The repair agent comes last, as the owner decided on 2026-11-17.

## Step 1: AGE-110, installer host support (done)

Merged into `main` as #25 together with AGE-109 (#24). The installer now sets up Codex, Claude Code or Cursor, but only **one** host per run (`packages/cli/scripts/installer-wizard.mjs`, `oneOf(HOST_NAMES)`). Choosing several hosts in one run moves to step 2a, as AGE-114 problem 5.

## Step 2a: AGE-114, installer

Covers AGE-114 problems 5 and 6, plus the installer checks from problems 2 and 4.

1. **Several hosts in one run.** The plan holds a list of hosts. Setup, registration and verification run once per host, and the report shows the result for each one. "All" is offered.
2. **Selection lists.** Hosts and workflows are picked from a checklist (arrow keys and space). Single choices such as tracker and documents mode are picked from a list. A summary screen comes before applying.
3. **Clear rejections.** Every rejected input shows a valid example. The help text and the parser accept the same forms.
4. **Non-interactive fallback.** Flags or environment variables give the same choices for CI.
5. **Setup proves it worked.** The installer checks that the knowledge server answers and that the knowledge store has content. If the store is empty, the step does not report success. It either fills the store or names the exact next action.

Split this out of AGE-114 as its own Story when planning starts.

## Step 2b: AGE-114, first session

Covers AGE-114 problems 1, 2, 3 and 4. Can run alongside step 2a, since it touches the plugins rather than the installer.

1. **Knowledge store.** The first session fills the store when it is empty, or asks to. `setup-project-knowledge` does not report success while the store is empty.
2. **Discovery writes through the server.** `discover-project-knowledge` uses `knowledge_put` and `knowledge_add` when the server is available, so version tokens and validation apply.
3. **Continuity.** The first session runs the Agent Continuity bootstrap and creates what checkpointing and resuming need. Find out first why the `SessionStart` hook produced no output in the test session.
4. **BMad options.** Starting feature work offers the BMad paths that fit the request (harden the idea, develop it further, check gaps) and runs the one the user picks. Plan this with AGE-112, which covers the same discovery experience.

## Step 3: AGE-113, native question and choice controls

Starts after step 2a, so the installer's selection lists and the session's choice controls follow the same rules.

Before planning, fill two gaps in the ticket:

1. **Fallback.** Scenario 2 is still the template. Proposed: when a host has no native control, show numbered text options with the same "Other" answer.
2. **Hosts.** Name which hosts must support native controls. The tests must cover at least one.

## Step 4: AGE-94, repair agent

Last, per the owner's decision on 2026-11-17. Design its scope first: which failures count as severe, how a workflow hands over to the agent, and what the agent may change without asking.

## Checks

Each step runs its own package tests while in progress, and the full suite once before pushing (see `AGENTS.md`). Steps 2a and 2b each get one requirements review on the pull request and one thermos pass.
